## 入口、数据与字节顺序

1. **选择受管扫描的可选准备阶段。** 拟在 `python -m polymarket_alpha_lab.papersim.cli run-scan --managed --config "$SCAN_CONFIG" --repo-root "$PROJECT_ROOT" --prepare-from "$INPUT_SET_SHA256" --operation-key "$SCAN_KEY" --attempt 1` 中加入 `--prepare-from`。它指向用现有 `papersim.snapshots` 登记的扫描输入清单。清单包含扫描配置摘要、时段和固定决策时刻、#118 发现批次摘要、队列/市场与模型原件引用、来源及采集证据。配置中的队列、模型、允许的盘口与输入一致。已有 `queues[].pack` 仍走既有读取路径。同一队列同时提供两种来源时明确报歧义。准备代码产生内存中的 JSON 数组，再经 `scan.records_from_pack`、`run_scan`、`assemble_scan`、`replay.bind_*` 和现有写者。准备代码可单独计算字节供测试，唯一业务写入入口为 `run-scan`。清单与原始响应是受管证据，临时市场包按需重建。旧批次引用其已登记的决策截点，后到的模型材料归入下一次满足时序条件的输入集。同一时段的原件只使用在该截点之前真实收妥的版本。
2. **共用 #118 的采集批次。** 现有 `d1compare.acquire.capture_inputs` 按 UTC 区间和标签封存 Gamma 事件分页、CLOB 两侧簿、请求序号、覆盖与成功回执。`read_capture(repo_root=…, batch_sha256=…)` 返回清单和原始 `JournalEntry`。核对同一受管实例、窗口、回执中确切输出摘要、每条请求的来源/序号、实收与来源时间、字节数和 SHA-256 后，才将原字节用于准备。在事件页面按事件和市场位置取出内嵌市场，验证 condition、market ID、标签与 token 的关联，使用清单对重复、冲突、未映射、超时和过期项的记录。旧 `packbuild.observations_from_journal` 只索引顶层市场对象，不能直接读取实际事件页。保留原页引用及位置，以买入 token 的真实 CLOB 档位计算可执行价和深度。B2 取价包复用相应时段同一批次和书的序号/摘要。B3 从后续真实时段的 `capture_resolution_inputs/read_resolution_capture` 取得按登记目标采集的终局，沿 #118 的 `settle --register-public-outcomes`、普通 `settle` 消费。以同一市场和原双方 token 贯穿来源链，终局另有自己的批次、时钟与生产方。B0 的证据截止于扫描时刻。
3. **先登记，再解析。** 现有受限采集入口按扫描配置取得缺少的原料。扩展其参数以选择输入组合，并在既有快照表封存上述小清单，返回其摘要。原件已登记时直接验证重放。网络仅经 `papersim.adapters` 的公共只读入口，显式打开既有公共读取选项，沿用 `FetchBudget` 的请求数、市场上限、单项/总字节、超时及整轮截止。同轮的多个来源共享剩余额度，包括重试及分页。分时段补采以独立回执关联，记录真实取得时刻。账面已花额度不能因换适配器而恢复。

   #118 候选的 `_collect` 在发现和盘口解析之后才批量调用 `_save_responses`。模型适配器的 `AdapterResult.evidence` 也可能在内部已解析之后才返回。对 FX-40 使用的在线入口，在通过状态、来源、正文边界和预算校验以后、第一次内容解析以前加入窄的原字节登记回调，沿用 `SnapshotRegistration`、`register_snapshot` 和受管连接。对获准保留的完整响应，先提交其内容并核验摘要和长度，再交解析器。保持同内容去重、每次请求单独计时、原批次幂等和既有清单版本的读回。用短事务登记单个原件，避免持有多份散列锁等待下一次网络读取。封存时重新核对原件引用并提交原有批次/回执。已登记而解析失败或进程中断的原件可以核查，未完成的输入集不能传给 B1。只允许重放已登记清单及当时截点能取得的原件。临时清单、重试和并发均不得产生第二份业务行。

## 取规格与组包

1. 在准备起始处由 `RegistryProvider.from_connection` 装入一次一致的角色视图，每个确定的扫描谱系取一次 `specs_for_lineage`。将该 `LineageSpecs` 映射同时交给报价与 B1 的 `assemble_scan`，保留旧文件包按 `consult_provider` 的使用方式。以 `active.spec_sha256()`、`active.model_version()` 绑定真正参与计算的规格，核对候选实际版本及 `scan_runs.params.provider.specs` 的活动规格。准备态记录固定选中规格摘要和模型输入引用，B1 拒绝同一操作的报价/规格错配。在准备模式的现有操作收据中绑定输入摘要、固定截点与该次实际选中规格的身份，利用现有快照表及注册表中的规范规格取回原视图。正常首次扫描自行选择活动规格。同一操作重试先按原键读回绑定（已成功则复用业务结果），换参数或换原件会留下冲突。角色更新即使发生在两次进程之间，原操作也能按原规格重新生成同一字节。下一次独立扫描另行取现役。当前 `RegistryProvider._merged` 返回生产基线 active，注册表中的再校准角色只在明细可见。正式换届与换回由 FX-39 第二步接入。
2. 足球沿 `soccer_model.candidate_for_market` 使用已登记的赛季/球队 xG、必要的桥接系数、市场种类、方向、盘口和买入簿。根据已选规格验证家族和参数。把返回的 `CandidateEnvelope.candidate` 作为可编码的 `SoccerCandidate`，保留十个变体、每侧中位数及实际构造所需的上下文。加密沿所选 `CRYPTO_GBM.fit` 取相应波动率，调用既有 `crypto_model.touch_probability` 或 `terminal_probability`，使用真实现价、已收盘 K 线、障碍、时段及合约方向。终值请求携带原始 `TerminalProbability` 与 `yes_when`，由 `pipeline` 做一次方向换算。`CRYPTO_GBM.predict` 对终值产生已经换向的类型，不能原样交给现行 pipeline。冻结规格使用既有精度和窗口。报价材料、新闻、费用、开赛/到期和桥接各按其证据填写，缺额维持既有拒绝或 blocked 语义。
3. 用现有 `replay.replay_bundle_payload` 编码请求。每个可识别目标产生一个稳定身份的成功请求或 `construction`，保留原摘要、缺项和确定的失败码。未取得足够身份的观察只计入有原因的采集覆盖。现有 `replay.bind_construction_failure/_run_constructor` 只重算足球构造器。用最小的封闭分派补齐准备所需的拒绝情形，保存可重算的输入/证据引用。重新重放必须得到同一原因。合法报价被准入规则拒绝时仍留下普通带报价候选。缺失原件、损坏封存或同键不同输入作为整次输入一致性错误拒绝，保留失败回执。不得把造出的价格、概率、新闻或空历史作为替代原料。
4. 对输入的队列、市场、方向、原始记录位置规定唯一稳定排序，保持簿和模型有序数组的业务次序。使用同一个既有序列化策略，固定 UTC/数字表示、字段次序、无效非有限数及编码，确定重复记录处理，输出长度和 SHA-256。时刻只取封存的决策截点，包内隔离实际运行时钟、随机数、数据库自增号、当前账户余额和文件路径。每行 `snapshot_refs` 保存已登记的原始 SHA，来源/序号等走其适当字段。现有存储会按裸摘要查表。包级摘要及证据引用放入现有受管扫描回执或该模式的已有参数位置。旧入口的冻结参数形状和请求编码按原样验收。
5. D1 新路径只负责调用上述受管命令。#118 候选的 `tools/d1_compare.py command_run_new` 通过 gate 后仍打印 argv 并返回 2。只把已满足原 D1 证据门禁的 Path N 分发接到真实子进程，给出输入清单、实际返回码和 B1 回执。用另一受管连接验证结果。实际源码如已完成分发则复用。模型计算放在受管 papersim 模块。Path L、时段登记与运营调度继续按其各自既有门禁。
