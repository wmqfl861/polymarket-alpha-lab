## 3. 公共来源、合约方向和三个时间

父采集器是唯一公共网络读者，使用原 `FetchBudget`、明确源名单、分页和实际限额。原始字节通过项目私有受管 PG 登记。来源有 Polymarket Gamma 市场/条款/赛程/价格参考、CLOB 两枚代币逐档簿，ESPN 足球赛程及适用的 NBA 终场，Understat/FotMob 的经验证输入、元数据与时效，原 κ 参数，Binance BTC/ETH 现价及冻结脚本要求的 K 线，完整运行需要的 Stooq WTI 辅助页。可用实现包括 `discover_markets/fetch_market/fetch_order_books/fetch_resolution`、`fetch_league_snapshot/assemble_xg_snapshot`、`fetch_fotmob_inputs/fetch_nba_inputs`、`fetch_closed_candles/fetch_spot`。当期 xG 指针目标与英冠/荷甲 sidecar 须以可取得的合格原件证实；历史优化样本只可证明解析/研究复算。缺批准的替代源或不新鲜时记缺，不用另一家同名资产的值填一侧。现场纪律禁止旧账连接与写入、生产历史导入、读取凭据或公网主机配置；子进程看不到数据库套接字、主目录凭据或公网。原库/脚本只读、固定 pin，重放仅能在前台子进程私有目录写临时输出，超时/信号需收回进程组。

1. **建立一次可追溯的方向映射。** 逐市场保存原 Gamma 标签、原顺序与 token 数组、条款、联赛/主客、盘口线/加时口径、crypto touch/terminal 和 above/below 等。YES/NO 依实际标签与对应位置；Over/Under 或队名结果需要从明确合约命题及两种结算结果双向推导“哪一枚 token 对应规范命题为真/假”。例如只在命题明确为“X 队胜”时，球队 X 对应 YES，另一侧依合约处理平局或作废；仅有两队名字并不定义 YES。改变输入排列应当保持 N 的语义与买入代币相同。重名、双方不唯一、平局/半场/终端方向未解、token/条件冲突，保留市场行并拒绝构造。市场结果 `YES-basket/NO-basket` 只适用于原有篮子条款。保存原始域、模型侧域、账本侧/类型域和胜方原 token 的对应关系。
2. **同一映射贯穿 B1→B2→B3。** B1 从买入 token 的真实 asks/bids 建请求与 DECISION；B2 按 scan、candidate、market/condition、side、原买入 token 核对实际观测，现行 `candidate_capture_target` 只返回 id 与开赛时刻，需在正式调用验证映射，错 token 即失败。B3 的公开终局先落于胜方原 token，经同一映射获得规范 outcome，再由 `select_entry_outcome/plan_settlement/ledger.settle_natural` 按入场方产生输赢/现金，不能把买 NO 又取一次补数。原 `polymarket.fetch_resolution` 对显式 Yes/No、有无一致性有既定语义；对支持的双标签/队名用同一已验证适配与原规则，未证明时 PENDING。验证 YES/NO 数组反序、Over/Under 反序、主客队名互换、三向/模糊市场、反向终端、同市场 YES/NO 两笔入场和候选不同时间再次进场。
3. **一份先验采集和三个时间。** 分开持久记录：①来源盘口/行情自身观察时间和系统完整收到该响应的真实 UTC；②本批统一 `decision_as_of`（全部被选输入真实收到后，在可用窗口内封存，永不从未来选最新值）；③实际执行、写入和重试动作时间。每个请求含单调序号、来源标识/公开参数、状态、来源时间、真实收妥时间、长度与 SHA；相同正文在两个时间点出现保持两个观察。嵌套分页保留原页裸摘要及到事件/市场/代币的路径，不能把重新序列化的子对象伪称原始响应。同 URL 多次、同 token 多簿严格选截止前的明确版本。响应内有源时刻时需满足源时间 ≤ 实收 ≤ 截止，用受审的簿年龄上限分别检查新鲜度；缺源时刻依能证明的既有来源合同标明“只有实取时刻”，达不到该合同即缺证。费用、模型数据、新闻和训练资料同样按首次可知时刻核对。
4. **迟到动作不能产生过去的纸面入场。** L 子进程在导入冻结脚本前固定其决策 `datetime.now/NOW`；N 以同一截止作 `EntryRequest.now/evaluated_at`，买簿采样和市场获取使用各自真实值。实际 DB、操作日志、时限仍走真实墙钟/单调钟。执行资格同时要求 `decision_as_of < kickoff_or_expiry`、实际准备入场及最终受管写入的授权检查点严格早于开赛/到期、市场仍开放、资料在当时仍新鲜。明确在数据库取得时段锁后、产生 entries/现金前最后复核动作时限，必要时限定事务完成窗口，若跨界结果无法证实则关闭入场并保留真实失败。恰好开赛、到期、迟到重启、迟收赛前源时间的盘口全部拒绝新入场/虚构 CLOSE。B2 现场采样须能证明在界线前已可见才是 CLOSE；界线和之后只能 PERIODIC。对可证明已在界线前实际提交的业务，重启后只读回原行。跨界后重算可标离线差异、不能计作准时入场。

### 5.1 公开终局如何由正常受管写者产生

#110 的 `adapters.polymarket.fetch_resolution` 从公共 Gamma/CLOB 取证，`store.MarketOutcomeObservation` 描述带来源的市场结果，`store_psycopg.record_market_outcome` 已提供按 evidence_key 幂等插入、碰撞比较和 outcome_id 读回。`settle --managed` 在 #104/#110 仅从已有 `market_outcomes` 选择实际适用的一行；从空历史结果表出发，前三者尚无已验证的日常业务入口将它们串起来。公开采集者、首次写入终局的人和最后完成结算的人必须分别留名。原生测试中直调 writer 预置结果不能作为该生产路径的验收。

**唯一实现路线。** 保留 §1 文件所有权：公开原件由采集写者通过 `acquire.py` 的正常 `capture-inputs/run-slot` 取得；真正插入 `market_outcomes` 的代码归既有结算写者，在 `papersim/settle.py` 增加经过复审的、可单独调用的“登记公开终局”阶段。协调者只接 `papersim/cli.py` 中 **settle** 子命令的一小段参数分发，与 Phase B 的 evaluate/report 片段按原规约顺序合入；受管 SQL 与锁由 §1 的唯一 store 写者负责。拟定的第一条正常命令为 `papersim.cli settle --managed --team … --repo-root … --register-public-outcomes <sealed-sha> --operation-key <writer-key> --attempt <n>`。它以实际登记模式收据名 `settle-register-public-outcomes` 单独产生结果；普通操作 `papersim.cli settle --managed --team … --repo-root … --operation-key <settle-key> --attempt <m>` 随后用现有规划读快照和现金写入路径消费。两次调用均记录实际部署代码、应用身份、实例与尝试。登记模式不能伪装成普通 B3 成功回执；两者的 evidence、输出数组和自然键独立。采集、登记、结算能顺次由同一无人值守时段触发，也能各自重启。

1. **采集和封存。** 先按原时段清单登记要核验的市场、双方 token 和对应的已证明开仓 entry（一个市场可关联多笔）；每个不同市场只采一次公共素材。父进程用正常 `fetch_resolution` 获取原 Gamma 市场和两侧 CLOB 响应，附实际采样和收妥时刻、两侧价格、解析状态和截止。适用全场体育条款时还要有符合范围的完赛/含加时材料及其来源。将每件原字节、原顺序、摘要、真实观测时间和可核来源在由采集器自己 operation/attempt 身份的受管事务封存；由成功回执发布这一版本的清单。对无持仓市场也保留实际观察和覆盖，不生成虚构 entry。网络失败、半套书、市场未 closed、终局冲突/未证实分别列明，日常结算对受影响原 entry 合法 PENDING。
2. **登记前重建事实。** 登记进程自其 STARTED/PREPARED 读取指定封存清单、复核 raw SHA/长度及真实采集 actor，并从原件重建适用的 `ResolutionObservation`。逐项核对 market_id、condition_id、slug 辅助身份、原 affirmative/negative token、实际胜方 token 与 §3 已登记双向极性；已知一边出现矛盾不能以另一 ID 或弱 slug 配上就通过。原生明确 Yes/No 的正常例需 closed、对应的终端角价与可信 CLOB 对照一致；缺少终局、冲突、互换 token、模糊双标签不得制造有效结果。VOIDED 只由合约认可的明确作废来源产生。核对比赛/到期规则及经济时点、来源确认和实际收到都没有越过时段可知截止，适用 entry 的来源/确认关系按 `select_entry_outcome`（含重新入场）验证；不把登记动作时刻写成原公开确认时刻。构造 `MarketOutcomeObservation` 的 typed IDs、双方 token、outcome/detail、observed_at、真实可证的 confirmed_at（未知保留空）、真实 source_kind（如 gamma_close）、source_ref 及源快照裸 SHA。可从清单还原多源字节和原观测，来源名称和数据库 actor 各自留存。对受支持的双标签须用已证条款认定胜方；不能证明时保留 PENDING，正常上报不支持的分母。
3. **原子写和归属。** 针对每一来源观察，以实例/区间/slot/登记模式/目标为稳定操作键、递增 attempt；另有按该观察的自然 evidence_key 取的数据库锁，以覆盖不同 operation 对同一市场观察并发。登记写者持项目受管连接，在同一外层事务用 `record_market_outcome` 完成已重建 typed observation 的插入或严格比对，读取 `outcome_id/evidence_key` 和所有已存字段；同时写不可变的分项业务回执及关联见证（模式、实际 actor、完整部署 SHA、原 capture key/attempt/seal、真实 writer key/attempt、绑定 entry 集合和当时读视图、原始观测/输出摘要、原行 ID、首次插入或本次复用状态）。事务回滚则两者都不可见。多项由真实登记批次收尾回执关联；登记结果可先于最终业务结算存在，原始 writer 身份不因此改变。普通 B3 在自己的独立 operation/attempt 内做新的真实一致性读取并记录其选择的 `source_outcome_id`，不继承登记回执，也不能以输出 FK 反证是谁插入的。
4. **提交、断连和首写找回。** 在业务事务提交前断开，查无结果和分项成功后才能按原清单重试。在提交后、首个进程尚未收到成功应答或尚未发布父批 SUCCEEDED 时断开，从新进程按原 operation、输入 SHA、自然键、原行 ID 和事务内的首写见证读回；完整相符记录新 attempt 的实际 RECOVERY_READ/完成，保留原 actor、原 attempt 与时间，余下只处理同一预定清单。若同样的行由另一 operation 先写入，本次仅能认领“复用”，应引用可证的首次 writer；仅存在结果行而无可证首写见证时，可以披露现存行/缺口，绝不自授首写身份。不同方向、确认时刻、原字节、来源、实例或 typed 身份等在同键发生冲突即保留首错、冻结该项。再次运行普通 settle 也只读回原 settlement 和唯一终端现金腿，不能重新回款。
5. **FX-35 家族 8 合同。** 当前 `evaluation_f.MarketOutcomeRecord` 的 writer 只接受 `settle` 和 `legacy_import`。该登记路径获审并部署后，应在 Phase B 的部署版本/真实 handler 对照中证明**实际**执行受管插入的是上述新版本 B3 登记模式（有自己的命令名、operation 和 attempt），其事务性首写证据连到相应的已证明 entry；这两项均证实才可按现有 `settle` 家族核验这条行。不能基于命令名字含 settle、同一 actor、终态成功、后来结算读到了它或相同时间作归属。老 #104/#110 B3 的读行为继续只代表消费；采集器只写原件时不产生 family 8 行。若实际写者确是独立 capture 命令、身份不明、没有真实 entry 链、缺部署映射，或合法需要记录无持仓市场的 typed 结果，应列原对象/真实 writer，按原证据区分可证的不匹配（FAIL）与缺证（NOT_ASSESSABLE）；已证窗内 legacy_import/旁路照原判失败。若另需第三类合法 writer，先单独复审和登记 F 合同，禁止把它映射成 settle 或 legacy_import、跳过该类行或因此声称 F 通过。不得为了 F 通过丢弃业务范围要求的公开结果。
6. **一正四反，均走普通进程。** 在一次性 Linux 项目受管 PG、真实迁移和应用角色上，先由获准测试准备与常规扫描建立一笔出处可核的开仓及其入场现金。独立 SQL 确认目标市场的 `market_outcomes`、`settlements` 和终端现金最初为零。然后让正式采集入口走真实 `fetch_resolution` 逻辑（原生 CI 可在公共传输边界用可分发的真实形状字节，标明来源）封存，运行正式登记模式，再从独立进程运行上述普通 `settle --managed`。SQL 与回执必须共同证明：一个原 outcome（原始来源/side/时间/首写 actor 正确），一个引用相同 outcome_id 的 settlement，一笔正确 Decimal 金额和类型的终端现金，既有开仓现金保持一笔。分别重启/重试两个命令、并发两次登记后，ID 与行数不变。负例依次为：① 源响应属另一市场、另一代币或极性不符；② 观测/确认越过截止、早于适用入场或不合全场/作废语义；③ 同一键换内容、去掉首写见证，或由另一实际 writer 写入再让普通 settle 读取；④ 逐目标写入后丢首次应答、当时成功与失败混在一批。前两者验证无有效 outcome/无回款且待定原因可读，第三类验证不认错 actor、冲突和 F 正确保留，第四类验证真实跨进程找回且只补余项。正常测试不得直接向结果表 seed 行或仅注入已构造的 outcome。待正式运营权限和现场原件就绪，再在真实前向时段复核；这组工程测试计零日。

## 6. 运行次序与逐日判定

启用前正本记录 Linux 干净执行提交、运行时清单、两 pin 源和归档、已审 G7/B2/B3/B4、执行节点独立合并、S1 实际定时器安装记录、实例别名/影子隔离及事前运行/比较合同。五个 `DayRunAuthorization` 事实要核对出处；完整字符串不能代替证据。D1 的模拟入场/现金/持仓只在影子实例，起始资金以可追溯的真实获准纸面来源为准，空实例标零/无暴露；不拷旧账、不补钱制造 entry。B1/FX-17 自身准入继续运行。无固定主机、可核执行权限或合格 xG 时，对应现场链仍待准备；无需重复申请已授研究/并跑权。

1. 使用现有受管 `stage --leg all` 或已验证的清单完成冻结还原。拟增 `tools/d1_compare.py register-interval` 在首日零点前登记未来 UTC 区间、时段网格、启动规则、覆盖/抽样分母、年龄与迟延预算和影子实例。定时器调用拟增 `run-slot --interval-sha256 … --scheduled-for … --slot … --repo-root …`。扫描 slot 封存输入后，用同一摘要/截止实际调用两腿 `run-frozen` 和 `run-new`，后者执行、等待和检查普通 `run-scan --managed`。每次失败保存真实 stderr 的脱敏代码与 PG 回执。手动诊断与自动调用使用同一处理函数。
2. 实际网格在开钟前固定。可沿用 00:05 扫描、小时取价/确认及赛前额外检查。B2 为全部应观察候选采集，B3 只使用可追溯公开终局和开仓后证据，歧义/冲突留待确认；篮球须全场含加时且条款匹配。收盘、中点、推算 NO、决策盘口和事后赛果在证据中分列。B4 在完成现金检查后用 `papersim.cli report --managed` 归档，日结引用该次实际报告键和正文 SHA；重试先找已归档的报告。独立回读 L/N 全部候选行、现金四项、两侧原料同源以及差异与终局样本。缺新闻/旧篮球用批准的缺项，其他单边/失配逐条记录成因与处置。
3. 日 D 的业务时间范围精确为 `[D 00:00:00.000000Z, D+1 00:00:00.000000Z)`。现有 `bankroll_daily_check` 的筛选条件是 `<= as_of`，而 key 只含 `UTC日+代码+最高计入event_id`，因此以 `as_of = 次日零点 − 1微秒` 做唯一正式日末检查。不能用次日零点、整秒 23:59:59 或提前获取未来 as_of。正式检查与报告在下一零点到达后进行；中途检查用只读查询或不同的已审核操作标识，避免正式日键在相同水位被提前占用。已有同键须核原始行 `as_of` 精确到微秒、身份、全部分项和旧报告，不能只凭 `inserted=False`。阈值 `abs(现金+未结本金−初始及调整−已实现净收益+未结入场费) ≤ 0.005`。
4. **水位与日切。** 以覆盖该实例所有 D1 业务写者的 PG 锁/屏障，在日末排空或列明未结束的原时段任务；等待已到日终的真实范围确认，在同一读视图记录现金事件水位、受影响 entries/settlements 的 ID/键、各表达到的写入回执与 D 日 slots 的终态，再查现金和归档。基础账户已有的账本字段可能使用 `entered_at` 或旧赛果的 `confirmed_at/evidence_time`；保存“源有效日、实际写入/事务完成日与回执时刻”两者。**尚未完成的资金操作不可用晚到写入把过期 D 伪成准时成功**。若 D+1 的正常 B3 用到 D 日已确认的结果并在既有账本口径下影响 D，保全 D 的原快照、check、水位、报告及结论，以新受管收据引用旧/新影响项、两次水位和因果时间；按原 D 截点重新审计并追加更正/重开是否仍有资格的裁定，绝不更新旧行或强迫伪造日期。原未齐全的 slot 即便重算平衡仍不算合格日。若同一 check key 已被占而事实不同，记录冲突并保持未认证；需要更细证据键时走单独评审变更，不调时钟、不造交易、不刷本金。已关日受追溯证据改变，冻结受影响的出口结论，从最后确能证明的连续期间重新评估。
5. **验收边界用例。** 测 D 日 23:59:59.000001、23:59:59.999999 以及次日 00:00:00.000000 三笔，前二计 D，第三计 D+1；测试同一水位的提前 check、跨零点提交、先分配低 event_id 后提交、迟到结算、断电恢复、跨日失败/重开。最高 ID 不能单独证明没有迟交，需原分项清单和受管日切屏障。运行日以事前网格与真实收据左连接。漏时段、时段内容变化、动作过时、现金不平、尚未处置的关键错误均如实保留。连续完整段遇缺口重开；修复会改变决策的代码、快照口径、冻结范围或配置后用新版本和新前向区间，不能拼接。

## 7. D1 出口、D2 生效与安全回滚

第一次真实烟测只证明接线。若自首个 UTC 日零点前已具备全部登记条件，随后每个 slot 都实际履行，该日可以计作第 1 天；半日、测试与历史观察不补足。D1 出口要有连续七个 **结束后已日结** 的 UTC 日及各自的收据、完整分母、所有差异归因处置和资金对账。差异三类为新库缺陷（修复并重开受影响正式区间）、冻结脚本漂移（记录历史影响及证据）、有意规则差异（按现有决定权裁定）。抽样 seed/选择域事前登记，按真实候选（含拒绝）逐位重放；无候选的当天记录分母为零。旧侧不写账，检验原金额/逻辑与零写入。独立审从托管库重算连续性、每笔抽样和可追溯性，任何未证项原样记录。

D1/切换端拥有写入受管 snapshots/command_run_events 的版本化时段、目标清单、原始观察、分项结果/恢复和切换凭证，提供原始生产来源、字段时序及摘要。Phase B 只读核验；原生工作流与分区清单（含 PAPERSIM_FILES）由同一协调者整合。D2 正式切换之前，独立阶段复审对 D1 给出结论，FX-35 Phase B 已在实际 `evaluate --managed` 及 `report --managed` 核实 F 的时段、现金、真实业务行及抽样来源。协调者先关闭旧调度的**新触发**，排空在途任务、确认子进程和未决事务/租约、记录最后一个旧侧及影子侧的真实成功时刻和代码，再启用正式受管目标与仓库定时器。D1 影子实例只读封存；通过实例身份、排程身份、角色、运行环境、查询范围和 report/performance 数据源核验绩效隔离，影子入场/现金/七天回执不得迁入正式业绩及 F 的 30 天分母。记录旧逐轮决策脚本的归档和无活动证据，形成“最后一次旧触发/完成、在途处置、正式切换实际生效时刻、首个实际新触发/完成”的链条；保留中间空隙或重叠、发生原因及归属，不能以启用时间代替成功执行。

首选把切换安排在未来登记的 UTC 零点，在零点已经完成排空且实际生效，才能把该 UTC 日期作首完整日。若真实切换在日内，记录真实生效的精确时间和剩余部分日，另行事前登记下一 UTC 零点为 F 的**首个完整 UTC 日**；不能把实际生效时刻向前取整。若计划切换未实际发生、错过预定零点，记录尚未生效的事实，在下一将来边界重新登记拟定切换。一旦正式切换已经生效，窗口锚点及原时段表固定：漏 slot、停机、重叠或未覆盖的实际时间隙留在原窗，按原 FX-35 项逐条判定，保留原窗 FAIL 或有证的未决状态，不能移动锚点重刷。若确需恢复，调度/值守责任人通过项目受管操作记录实际故障、最后成功、停止接单、在途处置、修复部署、授权值守岗位及交接人、恢复生效和第一笔真实成功的时刻/来源。出具独立复核的岗位/排程证据、登记新的运行区间与首完整 UTC 日后才开始一段新窗；原窗及两窗间空隙永远可查，已漏时段不由新窗抵销。向 Phase B 提供实际信号、首完整日、时段网格、源/真实观测与提交时间、水位、真实重试和空隙等证据；30 个完整日才按原标准评，D1 七天和切换日的部分时段不抵扣。

失去隔离、行为版本/时钟错误、出现跨期不明写入或现金不平时，停止新触发，封存并分类在途；有提交可能的工作先查真实业务/资金及回执，未提交且仍可取消的安全终止。保留两个实例的全部源、失败、操作与水位。仅在核对上一已审批的**仓库纸面**排程、目标实例及最后确认时段后才可恢复；不回启逐轮旧账写者。否则保持暂停。回滚/重开记录实际暂停、末次成功、恢复生效/首次成功与中间缺口，必要时重开连续观察窗，不能手工修账、对生产做历史导入、修改冻结区/V1 或删旧证据。
