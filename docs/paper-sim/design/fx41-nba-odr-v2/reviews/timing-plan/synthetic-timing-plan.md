# FX-41 NBA v2 合成计时执行计划

**交付对象为一名原生 Sol/max 实施者。** 复用现有全规模合成赛历、归档编码工具和新评分回调，补一个只在显式调用时运行的计时入口。它先可测量纯计算，待共享的 CLI/store 接入后，同一套合成字节用于项目原生 PostgreSQL 的端到端计时。本稿不包含耗时结论。真实研究运行仍按业主“批准单次方案，先登记再执行”的次序办理。

## 可复用的入口与当前缺口

源码核对基于 #114 实际合并提交 `d216059339dba9c3ca34d65813e9cf2ba98a0dd5` 及 `pal-nov21-fx41-nba-v2` 工作树中的纯实现。CodeGraph 在与该提交同 Git 树的已索引检出中定位了既有 `run_scoped_trials`、`select_common` 和留出判定路径。下列新增符号按工作树实际源码核对，最终计时需重新固定执行版本。纯实现已存在的工作树校验清单可沿用控制指针 `fx41-nba-pure-runner-focus-path.txt` 所指目录中的 `source-pins.sha256`。本稿读取时该清单的 SHA-256 为 `85cf0026f93e3d16d1c765f43f945edf4bba68ed964cc2e8578c03491d0fea22`，执行时须核对它是否还覆盖全部被测字节。

由同一人维护一个控制目录中的显式 pytest 文件，例如 `fx41_nba_v2_synthetic_timing.py`，容纳下述快速核对、纯计算及受管调用，共用输入生成器、计数器与回执格式。执行前检查同批是否已有覆盖这些环节的脚本，有则补齐并复用它。沿用既有 Linux 独立测试工作流，未来由实际本机 ZCode 从隔离目录显式选 `test_shape_smoke`、`test_full_pure` 或 `test_full_managed` 等拟建 nodeid，使用同一项目虚拟环境，只在受管节点显式装入项目原生数据库 fixture。计时文件放在常规 pytest 自动收集目录外，无需为长测改项目工作流。纯计时可在所属接口交接后进行，共享 CLI/store 仍按 FX 与 #118 的既有写权集成。

## 用一组可复验的合成输入贯穿计时

1. 给测试进程两个固定合成赛季、确定性生成种子（可用 `20261120`）和十进制合成事件 ID。对赛历使用已验证的来源日及每日比赛数，保留两个开季和最后后缀。搜索日计数可直接取控制目录 `fx41-nba-v2-metadata-preflight.voszjx2L/metadata-preflight.json` 的 `daily_search_team_coverage`（该文件 SHA-256 为 `9175d0474a4c4a490f6fce7d7e54224964e29b10c0b450065ddc2bd2669ea378`）。若需要完整 38 日向量，在单独的无评分元数据步骤由 `load_nba_odr_metadata` 导出日期和场数，并核对既有留出日计数摘要。评分进程只得到形状表和合成字节。也可先用 `odr_metadata` 的现有分布调通，再以精确日场数和同季历史前缀长度验收计时。
2. 沿用夹具中的合法球队标识与赛季规则，按固定规则分配合成对阵、主客和本方技术统计。各季须有 30 队、每队 82 场、首三日覆盖 30 队，每队每天最多一场。用可复现的变化产生非平局终场分、交错胜负、225.5 两侧结果和合理的技术统计，按已有公式重算归档中的双方回合数。验证数据足以触发实际评级、残差拟合、六项包络及后续统计。退化、全拒绝、单类或未收敛的夹具只能验证该异常路径。记录按季/日的前缀长度、每队历史深度、每日场数和拒绝数，可据此解释与预期规模的差异。
3. 用 `_season_bytes` 生成两份合成 gzip 和其**自己的** `NBAArchivePin`，独立规范编码合成成员及日计数。仅在隔离测试进程内为 `NBA_ODR_ARCHIVE_PINS` 和成员摘要安装合成身份。合成日程的计划和事件散列使用自己的字节。与正式日程对照的是日场数、同季前缀、完整规格、上下文共享及调用规模，不要求两个内容散列相等。完整计时使用真正的 `load_nba_odr_metadata`、`load_nba_odr_archives`、家族 `fit/predict` 与评分函数。复用 `odr_metadata` 时先取其形状并恢复它替换的加载器。拒绝将任一正式归档散列用于合成评分，从计时 worker 的输入中排除真实 gzip、历史记分卡、真实逐场终局和真实数据库配置。受管测试亦只认同一批合成散列，其测试注入不向产品 CLI 暴露开关。
4. 快速核对先用抛错的评分加载器及模型回调验证 `build_nba_odr_plan` 全程零评分，随后恢复真实函数。核对两季共 289 个搜索日，六个训练专用日 32 场，测试的 160+123 日共 2,124 场。断言 17 个有序完整规格各带原有六项包络，各折十七个不同规格、共享上下文、两目标掩码均正确。检查 4,811 个唯一物理身份、9,622 个目标使用，38 日/304 场的留出删去首日后为 37 日/295 场。先对极少数合成早日和长前缀回调核对输出类型、掩码、预测/拒绝和模型调用计数，然后用新进程冷启动完整计时。

## 完整计时怎样覆盖模型、嵌套选择和留出

| 测量段 | 实施与可核对的次数 |
| --- | --- |
| 准备与搜索 | 对**同一份**合成字节运行 `build_nba_odr_plan`，再构造一次 `_nba_odr_scoring_inputs(plan, content_by_season, deadline)`。按 `plan.trials` 的原次序交由 `search.run_scoped_trials`，每项恰调用一次 `replay.evaluate(item.spec, item.fold, item.targets)`。回调返回 `HoldoutEvaluation`。用运行器的 `_fixture_universe`、`_prediction_boundaries`、`_verify_batch` 取得按目标的 `.forecast` 后交回现有试验执行器。驱动仅接线和计时，不自写评分/择优算法。已接入受管计算时直接包裹同一实际调用点。核对 4,811 个开始、完成或中止身份及分目标掩码。满额完整证据要求全部走到回调末尾并核对状态。搜索最多有 `2,124 × 17 = 36,108` 个逐场预测机会，合计 72,216 个目标行机会，另列实际预测和拒绝。六变体是逐场预测内部成本，两个目标共享这次预测。 |
| 嵌套选择 | 用上一步的已核验批次，按实际 `nested_fold_ids` 和 `select_common(require_all=False)` 对每个谱系跑每个外折的严格同季内折，在外折构建实际记分卡，再用 `require_all=True` 作每目标一次全体外折的最终选择。合计 566 次外折嵌套调用及 2 次最终选择。完整早日情况下，各目标的外折前缀合计 `160×159/2 + 123×122/2 = 20,223` 个内折引用。核对逐折列表与实际计数，保留共同掩码、日均损失、校准、拒绝和嵌套结果的序列化成本。此处复用搜索批次，不另拟合。 |
| 两谱系都开放的成本 | 常规合成运行让程序择优并记录哪些谱系自然开放，现役胜出时该谱系照常零调用。为了覆盖可能的最大支出，另设**只对合成数据启用**的留出成本样例，提前从这 17 个规格中固定挑战者和实际比较规格，调用同一 `replay.evaluate_holdout`。两个目标各两侧，共 4 次顶层回调、`4 × 38 = 152` 次逐日单目标评估、`4 × 304 = 1,216` 个逐场预测机会。用真实批次验证、配对交集、两侧记分卡、覆盖/来源门、包络、既有 bootstrap 和符号翻转次数、Holm 与阶段一判定计时。保留合成来源门未评定。这个样例测量分支成本，不向常规选择器注入赢家，也不代表任何历史谱系实际开放。 |
| 计时边界 | 使用 `time.monotonic_ns()`，阶段边界分别记准备、搜索、嵌套、留出/统计、组装规范工件、CLI 及数据库提交。逐日聚合耗时、前缀与场数，必要时记录峰值 RSS 和工件大小。模型每场有严格历史配对、联盟背景、不同半衰期残差重算、球队评级和六个变体。完整调用已包含这些工作。父计时内的子计时仅用于归因。若双谱系成本另测，以实测双开段**替换**主测中已发生的留出/相关统计及其输出增量。对合成成本样例使用与正式相同的两侧配对、共同掩码和科学统计配置，记录各侧预测数和每目标最多 304 个配对身份。对双开工件的实际或保守有据的字节规模测序列化与发布，在合成常规路径自然双开时直接采用其整程。 |

纯计算阶段可先完成上述模型与选择测量，避免另写一份受管发布器或整套运行器。正式受管集成到位后，沿用同一驱动、数据和节点预算跑一次完整的正常入口，补齐前一版未覆盖的部分。若启动时两者均已就绪，直接用受管运行取得同一份搜索和嵌套分项，无须先重复一轮 4,811。

## 第一份可信的受管命令证据

使用项目测试的独立本机 PostgreSQL、干净的计时代码和测试进程内的合成来源/登记身份，先经正式实现的登记命令、第二连接读回、仅元数据预览，建立仅供测试的绑定。随后复用受管 CLI 的正常入口 `optimize run --managed --repo-root <隔离测试根> --family nba-pace-efficiency --as-of 2026-11-19T02:00:00Z --input-manifest <合成指针> --seed 20261120`。入口校验、`STARTED`、状态锁、已验证上下文、终态事务、工件写入和提交确认全部走真实实现。独立第二连接读回工件长度/散列和状态，核对同请求重放没有新科学计算。正式研究库与该测试库有不同的实例及证据身份，即使使用相同的日程文字也须用合成来源和登记记录辨认。历史评分数据的首次合法消费仍在正式研究库完成单次登记、独立读回和元数据预览之后，进入已授权的那一次非预览命令。

同一 CLI 入口建立的真实时钟为时间原点，计入清单验证及锁等待。观察最后计算边界、终态提交确认和正常命令返回。登记、预览及命令结束后的第二连接审计分别计时。正常命令内部的提交确认必须计入整程。未来执行不得沿用旧超时测试的短时钟、伪造的 `deadline`、空回调、短路统计或强制结果。受管绑定接线尚未就绪时，纯测只填已覆盖阶段，受管栏标为待测，其他并行工作继续。

**回执的最少字段。** 记录基线及实际被测整 SHA、未合并纯文件/测试夹具与计时驱动的 SHA-256、解释器和依赖版本、主机别名、CPU/配额、并发负载及冷热状态。记录生成种子、每季合成原始/解压字节长度与摘要、成员/日表摘要、比较者与 17 个完整有序规格/六变体身份、共享上下文、计划及元数据长度和摘要、各段开始/结束单调时刻、状态计数、真实函数调用数、自然开放与成本样例各自的统计量及工件大小。受管回执另记脱敏实例身份、代码与登记/运行原 ID、时钟分配、实际终态及第二连接读回 SHA。短时诊断、纯组件全量和实际受管命令分别标清证据来源。早期工作树耗时可帮助优化，最终资格以实际支持版本上的相同工作量和环境为准。

**判读方式。** 已有实现须经保守实测支持从 CLI 入口至计算完成 **严格小于 3,540 秒**，整条命令 **严格小于 3,600 秒**，含 60 秒收尾预留。若自然开放场景较轻，列示经过双开成本替换的保守总数、实测收尾和剩余余量，以及每个未覆盖成本的依据。搜索平均可用空间 `3540/4811 ≈ 0.736` 秒尚未扣除其他阶段，不能当成单次上限。首日、少量长前缀、空回调、旧单季超时回执、六与十的比例或均值乘 4,811 都不能给出全程的严格上下界。容器争用、仪表开销和工件规模须随数字披露。若实际到期，保存首次停止时刻、已完成/中止/未启动的数量与阶段。若仅有样本或遗漏阶段，记“时钟未证”。任一保守总数触及相应界限时按已批准计划记录当前版本的 `NO-GO` 和差额，限定在所测条件。需要优化时优先从实测热点出发，用同一合成输入按原有数值精度和规范编码对照预测、拒绝、嵌套赢家、规格、共同掩码与工件，保留物理试验计量后重测。
