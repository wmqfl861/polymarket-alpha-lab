# 05 开发计划（2026-11-19）

这份计划覆盖三件事：把纸面闭环搬进仓库（M2 收尾）、新增"模型自动优化"（下称优化线，节点编号 MO）、治理和归档。设计依据见 [04-optimizer-design.md](04-optimizer-design.md)，修复条目见 [03-fix-list.md](03-fix-list.md)。

估算单位是"代理工作日"：一个开发代理连同它的计划复审、代码复审走完一个节点所需的日历天数。它是排期用的粗估，不是承诺。

## 1. 总览

```
现在 ──────────────────────────────────────────────────────────────────────────────────────►
主线   M2 收尾：FX-26 ─► run-scan ─► capture-marks / settle / report ─► 7 天并跑 ─► 切换 ─► M4 每周评估
                 │            │                    │
优化线  MO-0 ─► MO-1 ─► MO-2 ─┼─────────────────► MO-7 影子并行 ─► MO-8 判定与换届 ─► MO-9 报告 ─► 每周运行
        （离线部分，与主线并行）  MO-3、MO-4、MO-5、MO-6                         MO-10 加密、MO-11 新联赛、MO-12 设计
治理    FX-28 文档入库、FX-33 过期文字、FX-25 规则草稿、FX-32 分支保护（owner）
归档    FX-18 分批归档（本轮解锁，独立工作树）
```

三条原则：

1. **先闭环，后上线。** 优化线里只有离线部分（MO-0 到 MO-6）可以现在开工。影子并行和换届（MO-7 到 MO-9）必须等 `run-scan` 和 `capture-marks` 落地。没有闭环，就没有前向数据，优化器无从确认任何候选。
2. **接口先定。** `run-scan` 动工之前，先把"扫描时按谱系取模型规格"的接口定下来（04 第 10 节），`run-scan` 从第一天起就经它取规格。注册表为空时它返回冻结基线，所以这不增加 `run-scan` 的风险。
3. **优化线不抢主线的人手。** 主线的四个命令优先。两边共用的文件（迁移目录、`store*.py`、`evaluation.py`、`cli.py`）按第 4 节的单写者规则排队。

## 2. 主线：M2 收尾

节点划分沿用现有的 M2 计划（B1 `run-scan`、B2 `capture-marks`、B3 `settle`、B4 `report`、D1 并跑、D2 切换）。本轮审核给它们各加了几条验收条件：

| 节点 | 本轮新增的验收条件 | 来源 |
| --- | --- | --- |
| 前置 | FX-26 先合入：候选带比赛键和开赛时间 | N-1 |
| B1 `run-scan` | 经 `optimize/provider.py` 的接口取模型规格（注册表为空时等于冻结基线，输出与不接时逐位相同）；每个候选写入比赛键和开赛时间；暂停状态落库并跨重启保持（FX-17 的接线）；扫描回执记录代码提交号，工作区不干净就拒绝运行 | 04 第 10 节；FX-17；FX-03 |
| B2 `capture-marks` | 收盘价必须早于开赛（FX-34）；对全部候选取价，不只是入场的；覆盖率进报告 | N-2；FX-34 |
| B3 `settle` | 逐笔结算；多条查询的读取用一致性快照（FX-29） | N-4 |
| B4 `report` | 评估按比赛键聚簇（FX-26）；C、D 的覆盖率下限（FX-27）；A 不计构造失败（FX-30） | N-1、N-2、N-5 |
| D1 并跑 | 至少 7 天；每条差异归因；每天现金恒等式 | 原计划 |
| D2 切换 | 标准 F 的判定接上运行证据（FX-35），30 天计时从切换日起算 | I-1 |

M2 的出口标准不变（原开发计划第 6.3 节），另加一条：FX-26、FX-27、FX-29、FX-34、FX-35 全部合入。

#### MO-1 模型规格和模型族接口 ｜纯函数｜1.5–2 天

- 新文件：`papersim/optimize/__init__.py`、`optimize/spec.py`、`optimize/families/__init__.py`、`optimize/families/base.py`、`optimize/families/soccer_frozen.py`、`tests/test_papersim_optimize_spec.py`。
- 要点：
  - 规格的规范化文本（数值写成十进制字符串、键按字典序）和 SHA-256。
  - 模型版本字符串：冻结基线原样沿用现在的两个字符串（`papersim/pipeline.py:117-118`），这样已有数据的队列身份不变；其它规格用"估计程序版本加校验值前 12 位"。
  - 冻结生产模型包成一个没有可调参数的模型族，作为各足球谱系的基线。
- 测试：同一组参数换键的顺序、换浮点写法，校验值不变；改任何一个参数，校验值必变；基线的版本字符串等于现有常量；`policy_code_sha256()` 的值与合入前相同（把当前值钉进测试）；导入这个子包不会带入数据库驱动或联网模块。
- 验收：离线全量通过；自检十项输出逐字节不变；命令行启动加载的模块数不变。

#### MO-2 注册表：迁移和存储 ｜数据库泳道，排在 FX-26 之后｜3 天

- 新文件：`database/papersim/migrations/<时间戳>_papersim_model_registry.sql`（六张表，见 04 第 9 节）、`papersim/optimize/registry.py`、`tests/test_papersim_optimize_registry.py`、`tests/test_papersim_optimize_registry_native.py`。
- 改动：`database/papersim/migrations.lock.json`、`papersim/store.py`（六类记录的校验和幂等键）、`papersim/store_psycopg.py`（写入和读取）、迁移清单的测试、工作流的 papersim 清单和 `PAPERSIM_FILES`。
- `registry.py` 是纯函数：从角色事件序列推出每个谱系当前的现役、基线、候选、守卫，并检查不变量——恰有一个现役；基线永久存在；候选不超过两个；守卫不超过一个；换届的两条事件（旧现役转守卫、候选转现役）必须在同一个事务里；解冻事件的决定者不能是自动规则。
- 提供初始化函数：把各模型族的基线规格和初始角色写进注册表，幂等。对应的命令 `optimize init` 在 MO-6 接入命令行。
- 测试：防改触发器拒绝更新、删除、清空；同键同内容重写读回原行，同键不同内容失败；事件缺失或顺序不合法时报错，提供者回落到基线；空表等于基线。
- 验收：真实数据库分区通过；迁移清单测试按 03 第 0 节第 3 条的做法更新。

#### MO-3 评估内核 ｜纯函数｜3–4 天

- 新文件：`optimize/metrics.py`、`optimize/walkforward.py`、`optimize/scorecard.py` 和各自的测试。
- 复用而不是重写：评分用共享的 `research_probability_scores`；聚簇重采样用评估模块里已冻结的实现（把它提成公开函数，输出不变，由现有的回归数字保证）。
- 功能：二分类和三分类的对数损失与 Brier；配对差及其聚簇区间；符号翻转检验和 Holm 校正；分桶校准、校准斜率与截距；按完整比赛周、比赛日、到期日扩张的折；嵌套选择；一倍标准误规则；各族验证门 A–E 的统一计算。
- **回归锚点**（已发表的数字必须由新内核原样算出）：
  1. 新足球 30 个格子的 Brier（输入是仓库里的 `new-soccer/holdout_predictions.csv`，对照 `evidence/recompute_new_soccer_output.txt`）。
  2. NBA 报告里的各行对数损失（输入是 `nba/predictions.csv`，对照 `evidence/recompute_nba_output.txt`）。
  3. WP-P4 的 360 场配对比较：生产 1.009471、再校准 1.011281，差 +0.001811，区间 [−0.007597, +0.010589]。它的输入在服务器的研究目录里，这一条在服务器上验证，并把输入登记为快照。
  4. 评估模块 10-30 快照的全部回归数字不变。
- 测试：对每个折生成器做"未来行注入"——加入截点当天及之后的比赛，折的内容和历史预测必须不变。
- 验收：四组锚点全部复现；同样的输入重跑结果逐字节相同。

#### MO-4 数据集层 ｜3–4 天

- 新文件：`optimize/dataset.py` 和测试。
- 把 `tools/wp_p4_history.py` 里的纯逻辑（历史比赛、赛程、折、`history_at`、`build_folds`）移进库，工具文件保留为薄封装，原有测试不改并继续通过。
- 契约：比赛记录（开球时间、何时可用、联赛、赛季、轮次、双方、比分、xG）、市场观察（比赛键、盘口类型、盘口线、方向、观察时间、买价卖价中间价、来源）、结果、数据集清单（引用的快照校验值、行数、起止日期）。
- 三类来源：已登记的快照（Understat、FotMob、国家队、ESPN、K 线）；受管库里的候选决策价、收盘价和结果；冻结的研究文件（只用于回归锚点）。

- 验收：每个构造器都过"未来行注入"测试；同样的快照得到同样的数据集摘要；缺字段、重复比赛、时间倒置都明确拒绝并给出原因。

#### MO-6 搜索、运行器和命令 ｜3 天

- 新文件：`optimize/search.py`、`optimize/runner.py` 和测试；`papersim/cli.py` 增加 `optimize families`、`init`、`run`、`status`（按需导入）。
- 一次运行的回执写进 `papersim.command_run_events`；逐试验成绩和逐场预测登记为一份快照；`papersim.optimization_runs` 写一行。
- 测试：
  - 确定性：同样的快照、规格、种子、提交号，重跑的产物逐字节相同。
  - 预算：超过时间或试验数上限时以"运行失败"收尾，保留已完成部分，不静默截断。
  - **规则本身的假阳性率**：在"两组参数实际同样好"的合成数据上用 200 个不同种子各跑一次，登记候选的比例不得超过 5%。在"确实好 0.02"的合成数据上，登记比例不得低于 80%。
  - 多谱系同时评估时做了 Holm 校正；没过留出期的规格 28 天内被拒绝重提。
- 验收：对俱乐部足球、国家队、NBA 各完成一次真实历史数据的运行，结果和记分卡记入 `DELIVERY_PLAN.md`。结果是"没有更好的"同样算完成。

**第一阶段出口。** MO-0 到 MO-6 合入；两条 CI 为绿；注册表为空时所有现有行为逐位不变；三次真实运行的记分卡入档。这时优化器可以离线使用，对扫描没有任何影响。

#### MO-8 判定和换届 ｜3 天｜依赖 MO-7、B2

- 新文件：`optimize/policy.py` 和测试；`cli.py` 增加 `optimize score`、`decide`、`apply`、`rollback`、`freeze`、`unfreeze`。
- `policy.py` 是纯判定，带规则版本号；数字只在这一个地方定义。
- 测试：
  - 表驱动：04 第 6 节每一条规则的边界值各一例。
  - 性质：配对差更负，结论只会更有利于候选，不会反过来；样本不足时永远不出"晋级"。
  - 暂停继承：被暂停的谱系换届后仍然不能入场。
  - 现役队列入场满 30 笔时，结论是"晋级，待确认"，不写角色事件。
  - 28 天内第二次换届被拦截；冻结后不登记、不换届；解冻不能由自动规则写入。
  - 同一个证据水位上重复判定，得到同一条判定记录。
  - 回退：新现役显著更差时换回守卫，候选退役。
- 验收：在隔离库上演练完整的一轮——登记候选、影子、判定、换届、换回。

#### MO-9 报告和节奏 ｜1.5 天

- 定时任务的条目写进使用说明，实际加到服务器上由切换节点（D2）一并做。
- 状态板每周更新"模型自动优化"一行。

**第二阶段出口。** 至少一个谱系在真实扫描上走完"登记候选、影子、判定"的一整轮（结论可以是退役）；做过一次回退演练和一次冻结解冻演练；周报连续出了两期。

| 优化线第一阶段（MO-0 至 MO-6） | 约 22–30 个代理工作日（其中 MO-5 的五个子节点占 8–12 个，可并行） | 约两周 |
| M2 收尾（含 FX-26、27、29、34、35） | 约 12–16 个代理工作日，另加 7 天并跑 | 约三周 |
| 优化线第二阶段（MO-7 至 MO-9） | 约 7–8 个代理工作日 | `run-scan` 和 `capture-marks` 合入后约一周 |
| 第一个候选的结论 | 取决于数据 | 俱乐部足球大小球类：换上去之前至少 3 周影子；胜平负至少 5 周 |
| 优化线第三阶段 | 约 10–14 个代理工作日 | 第二阶段之后 |

需要说在前面的两点：

- **很长一段时间里，优化器的每周结论都可能是"没有更好的"。** 按 11-19 的数据，这是最可能的结果，也是正确的结果。它的价值首先是把"试过什么、为什么没用"留成统一口径的记录，不再靠一次性的脚本。
- **自动优化不会缩短晋级时间。** OD-G 的样本按模型版本累计，换一次现役就重新数。量最大的队列在 M2 切换后约两个月才有第一次晋级评审，这个估计不因优化线而提前。

## 6. 上线后的每周节奏

并入原计划的 M4。每周二做四件事：

1. `optimize run`：对每个模型族做一次历史运行。
2. `optimize score` 与 `decide`：刷新影子统计；样本到了预定点的谱系做判定。
3. `evaluate`：各队列的评估报告，以及 OD-G 六条的状态和暂停规则。
4. `optimize report` 与状态板：登记本周的候选、换届、换回、退役，以及"没有更好的"。

需要 owner 看的只有三类事：现役队列入场满 30 笔后的换届建议；某个队列六条全部满足时的晋级评审材料；任何暂停。其余按规则自动进行并留档。

## 7. 风险和应对

| 风险 | 应对 |
| --- | --- |
| 搜索空间被一点点加大，比较次数失控 | 搜索空间版本化；扩大要走节点计划和复审；记分卡里始终写明本次比较了多少组 |
| 规则在看到结果后被改 | 数字只在 `policy.py` 一处定义并带版本号；登记日写进 `DELIVERY_PLAN.md`；改数字要另行记录并重新登记 |
| 影子计算拖慢扫描 | 每个谱系最多两个候选；扫描耗时进回执；超预算时先丢影子、不丢现役，并留下记录 |
| 注册表出故障导致扫描停摆 | 提供者读不到就回落到冻结基线 |
| 频繁换届让晋级样本一再清零 | 每个谱系 28 天最多一次；现役队列入场满 30 笔后改为 owner 确认 |
| 历史数据在服务器上，仓库里核对不了 | 数据集清单加快照登记；回归锚点第 3 条在服务器上验证并留证 |
| 模型源码参数化时不小心改了数值 | 默认参数下逐位不变的测试是 5b、5c 的硬性验收；冻结的生产模型一律不改，只包一层 |
| 归档与开发互相踩文件 | 归档用独立工作树，每批变基；两边共用的测试清单由数据库泳道统一改 |
