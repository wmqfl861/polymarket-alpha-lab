**owner 答复之后本地做什么。**

5. 做一次经固定入口的自然投递，回执入库，不含收件人标识和正文。

7. 旧路径在 Windows 上留下的东西（任务目录，给代理续用的那个会话）列出来报告 owner，由 owner 决定清不清理。
8. 登记剩余风险：远程控制通道能做的事比这一个入口宽，工具没有按命令限制的能力。写明现状、owner 知情，以及以后想收窄时可以走的方向。这一条是登记，不是切换的前提。

**如果在 `RemoteSigned` 下脚本仍然起不来**（比如放上去的文件带了"来自网络"的标记）：停下来，把退出码和现象报告 owner。不要自行换成更宽的值，不要自行去掉文件的标记。

**切换之前。** 11-24 的临时约束继续有效：不扩大运行层（消息类型、收件人、正文里的外部文字来源、联赛、市场、下注规则），不放宽现有的核对，不增加重试。切换之前要不要先停掉两个通知定时器由 owner 定（`DELIVERY_PLAN.md` 第 88.4 节写了怎么停）；owner 不说就维持现状，因为 owner 两次明确说过保留微信链路。

**怎么验收。**

- `main` 上有改过的 `launcher()`（选 A 时）和对应的用例。
- 库里有 Windows 现场六种情况的输出，六种的退出码符合预期。

- 登记里有：服务器检出的提交号；现场读回"搜不到代理调用"的结果；剩余风险的那一段；owner 对 OD-Z、OD-AA 的原话。

**不要做的。**

### FX-36（续）仓库公开的收尾 ｜R7-2｜P2｜决定项 OD-M

   - 如果结论是"从外面能连上，并且接受口令登录"：当即报告 owner。改不改、怎么改由 owner 定。改之前先确认有一条已经验证过的、不依赖口令的登录方式，免得把自己锁在外面；改完从外面复查一次。
2. **第二条限制的加载次序。** 不要为了测那个窗口去重启服务。先只读地写清楚现在的加载次序和它依赖什么；给 owner 一个方案，把它调到端口发布之前，或者放到不受发布次序影响的位置；owner 授权之后再改，改完从外面复查一次，结果入库。
3. **`main` 的保护。** 见第 2 节 OD-M。这是 owner 在 GitHub 上的操作，本地不要代做。

**怎么验收。** 第 84.2.4 节里有登录入口的两个结论和时间；有第二条限制的现状说明，以及 owner 的决定和改后的复查结果（如果 owner 决定改）；GitHub 上读得到对 `main` 生效的规则。
